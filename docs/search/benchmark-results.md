단일 검색의 응답시간을 확인한 뒤, 검색이 겹치는 상황에서도 지연이 반복되는지 같은 조건으로 세 번 측정했다.

응답시간은 첫 페이지와 스크롤 후속 요청을 함께 집계했다. 구간은 요청 시작 시각으로 나누고, 워밍업과 종료 후 남은 요청 처리는 위 구간별 P99에서 제외했다. 실제 API 요청률은 지속 구간 13.49~13.51 RPS, 피크 구간 24.87~24.92 RPS였다. 아약스는 첫 요청으로, 일치 글이 10건인 오버래핑은 두 페이지로 종료됐다.

2회차 Grafana에서 피크 부근 MySQL EC2 CPU는 약 80%, HikariCP 연결 대기는 최대 4건이었다. 부하에서 지연이 반복되는 것을 확인한 뒤, 검색어별 실행 계획으로 게시글 검사와 정렬 과정을 확인했다.

<summary><strong><span style="font-size: 1.2em;">5. 얼마나 빨라졌고, 어떤 한계가 남았는가?</span></strong></summary>

**최신순 검색에서 기존 PK 인덱스를 활용해 필요한 결과를 찾으면 조회를 종료하도록 변경했다.** 첫 페이지 실행 계획에서 별도 정렬이 사라졌고, 결과가 많은 검색의 검사량이 크게 줄었다. 결과가 드물거나 없는 검색에는 검사량이 남았다.

### 실행 계획으로 확인한 변화

첫 페이지 `LIMIT 6` 기준이며, API 응답에 반환할 5건과 다음 페이지 유무 확인용 1건을 조회한다. 데이터는 벤치마크 10,000건과 기존 글을 합친 10,002건이다.

| 검색어 | 결과 특성 | 변경 전 검사 게시글 | 변경 후 검사 게시글 | 변경 전 SQL 시간 | 변경 후 SQL 시간 |
|---|---|---:|---:|---:|---:|
| 김민재 | 일치 글 1,000건 | 10,002건 | **43건** | 59.8ms | **0.375ms** |
| 오버래핑 | 일치 글 10건 | 10,002건 | **5,400건** | 58.6ms | **33.6ms** |
| 아약스 | 일치 글 없음 | 10,002건 | **10,002건** | 56.6ms | **60.7ms** |

변경 후 세 실행 계획 모두 `Index scan on p using PRIMARY (reverse)`가 나타났고 별도 `Sort` 단계는 없었다. 김민재·오버래핑은 일치하는 결과 6건을 확보한 뒤 종료했다. 아약스는 끝까지 검사한 뒤 0건을 반환했으며 작성자·이미지 조인은 실행되지 않았다.

위 시간은 각 조건을 한 번씩 실행한 `EXPLAIN ANALYZE`의 실제 시간이다. API 응답시간이나 반복 측정의 백분위수가 아니다. 아약스의 56.6→60.7ms만으로 일관된 성능 악화를 판단하지 않고, **결과가 없을 때 검사량은 줄지 않았다는 사실**로 기록한다. 최적화 후 수치는 사용자가 MySQL 세션에서 실행해 공유한 실행 계획을 기준으로 작성했다.

최적화 전 3회와 4절의 최적화 후 API 전용 재시험을 비교한다. 벤치마크 데이터 1만 건, 검색어 3개, 검색 시작 5→10→5회/s, 10분 구간 구성과 검색·스크롤 조건은 동일하다. 계측 추가 및 모니터링 구성 변경은 각 실행 조건에 구분해 기록한다.

| 회복 구간 API P99 | 718.82~875.64ms | **80.01ms** |

| 실패·타임아웃·실행 누락·중단 | 각 실행 모두 0건 | **모두 0건** |

### 이번 결과의 범위와 남은 한계

<summary><strong><span style="font-size: 1.2em;">1. 데이터가 10배 늘어나자 검색 지연 발생</span></strong></summary>

2026-11-11 (KST), #100

기존 벤치마크 게시글 1만 건에 9만 건을 추가했다. 검증한 일치 건수는 김민재 10,000건(10%), 오버래핑 100건(0.1%), 아약스 0건이었다. 1만 건에서 최적화한 검색 쿼리와 검색·스크롤 부하 조건을 그대로 사용해 세 번 측정했다.

부하는 워밍업 2분·지속 5분에 검색 시작 5회/s, 피크 1분에 10회/s, 회복 2분에 5회/s였다. 세 검색어를 약 ⅓씩 선택하고, 페이지당 5건씩 최대 10·25·50건을 30%·50%·20% 비율로 탐색했다. 후속 페이지까지 2~5초 기다렸다.

| 측정 | 1만 건 최적화 후 | 10만 건 1회차 | 10만 건 2회차 | 10만 건 3회차 |
|---|---:|---:|---:|---:|
| 전체 API P95 | 71.37ms | 14.76초 | 14.83초 | 14.53초 |
| 지속 부하 API P99 | 81.74ms | 961.69ms | 954.52ms | 955.37ms |
| 피크 API P99 | 83.10ms | 25.58초 | 26.19초 | 25.93초 |
| 회복 구간 API P99 | 80.01ms | 21.13초 | 20.17초 | 20.59초 |
| 검색·스크롤 요청 | 8,909건 | 11,856건 | 11,861건 | 11,855건 |
| 검색 시작 누락 | 0회 | 122회 | 121회 | 123회 |
| 요청 실패·타임아웃 | 0건 | 0건 | 0건 | 0건 |

**세 번 모두 피크에서 지연이 크게 증가했고, 검색 시작 누락이 발생했다.** 피크가 끝난 뒤에도 회복 구간 P99는 20초 이상이었다. 전송된 API 요청은 모두 성공했지만, 예정된 검색 시작을 일부 수행하지 못해 세 실행 모두 실행 누락 0회 기준을 통과하지 못했다.

### 스크롤 후속 요청에서도 지연이 나타났는가?

전체 응답시간과 구간별 P99에는 첫 페이지와 후속 페이지 요청이 함께 포함된다. 실행별 첫 페이지 요청은 3,176~3,178건, 스크롤 후속 요청은 8,679~8,683건이었다. 전체 실행 구간에서 따로 집계한 P95는 첫 페이지 16.07~16.66초, 후속 페이지 13.54~14.10초로, 두 요청 모두 지연됐다.

오버래핑의 일치 글이 10건에서 100건으로 늘어 같은 탐색 규칙에서도 후속 요청이 증가했다. 실제 API 요청률은 지속 구간 18.68~18.72 RPS, 피크 구간 18.38~18.62 RPS였다. 검색 시작 속도와 함께 실제 페이지 요청량도 기록했다.

### 어느 검색에서 먼저 지연이 보였는가?

지속 구간의 검색어별 P95는 김민재 43.17~59.89ms, 오버래핑 163.43~174.92ms, 아약스 995.58ms~1.02초였다. 피크에서는 세 검색어 모두 P95가 16초 이상으로 늘었다. 이어서 같은 시간대의 DB 사용량과 연결 대기를 확인했다.

1·2회차 Grafana 캡처에서 MySQL EC2 CPU는 지속 부하 구간에 약 83%였고, 피크 전후에 100%에 도달했다. 같은 시간대 백엔드 EC2 CPU는 한 자릿수였으며, HikariCP에서 연결을 기다리는 요청은 약 190개까지 증가했다. 그래프상 5xx 요청은 관측되지 않았다.

두 실행에서 **MySQL CPU 포화, DB 연결 대기 증가, API 응답 지연**이 함께 관측됐다. 개별 쿼리의 검사 행 수와 실행 시간은 이 지표에서 측정하지 않았다.

<summary><strong><span style="font-size: 1.2em;">3. 결과가 없는 검색은 10만 건을 모두 검사</span></strong></summary>

부하 테스트를 마친 뒤 같은 검색 쿼리의 첫 페이지를 검색어별로 한 번씩 실행했다. 첫 페이지의 `LIMIT 6` 조건으로, API 응답에 반환할 5건과 다음 페이지 확인용 1건을 조회했다. 기존 게시글 2건을 포함한 전체 테이블 행 수는 각각 10,002건과 100,002건이었다.

| 검색어 | 1만 건 검사 행 | 10만 건 검사 행 | 1만 건 SQL 시간 | 10만 건 SQL 시간 | 10만 건 반환 행 |
|---|---:|---:|---:|---:|---:|
| 김민재 | 43건 | 47건 | 0.375ms | 0.411ms | 6건 |
| 오버래핑 | 5,400건 | 5,814건 | 33.6ms | 36.5ms | 6건 |
| 아약스 | 10,002건 | **100,002건** | 60.7ms | **595ms** | 0건 |

검사 행 수는 `Index scan on p`의 실제 반환 행 수이며, SQL 시간은 최상위 `Limit`의 완료 시각을 기준으로 기록했다. 세 검색 모두 기본 키 인덱스를 역순으로 읽었고 별도 정렬은 없었다.

김민재와 오버래핑은 일치하는 6건을 찾고 스캔을 멈췄다. 아약스는 일치하는 글이 없어 **게시글 100,002건의 제목·본문을 끝까지 검사**했고, 작성자·이미지 조인은 실행되지 않았다. 아약스의 검사량은 약 10배, 단일 SQL 실행 시간은 약 9.8배로 늘었다.

이 비교는 첫 페이지 SQL의 단일 실행 결과다. 부하 중 API에서 관측한 대기 시간과 검색어별 기여도는 이 실행 계획에서 측정하지 않았다.

# 게시글 LIKE 검색 성능 검증 계획

**기준 브랜치** `search-enhancement` · **상태** 시험 조건 구체화 중

현재 구현한 제목·본문 LIKE 검색을 기준으로 데이터 증가에 따른 한계를 확인하고, 측정 결과를 근거로 개선한다. 계획과 시험 코드·측정 결과를 이 저장소에서 함께 관리한다.

**진행 흐름**

목적·목표 정의 → 데이터·시험 조건 확정 → 소규모 적재 검증 → 기준 성능 측정 → 원인 분석 → 개선·재시험

## 1. 무엇을 확인하려는가?

제목·본문 LIKE 검색 API와 검색 화면 연결, 브라우저 뒤로 가기 복원을 완료했다. 백엔드 EC2와 MySQL EC2를 각각 한 대씩 사용하는 실험 환경에서 검색 성능을 검증한다.

### 어떤 상황을 검증하려는가?

경기 직후에는 특정 선수나 경기 장면을 찾는 검색이 집중될 수 있다. 게시글이 누적되면 같은 검색어를 사용하더라도 조건 확인과 정렬에 필요한 작업이 늘어날 수 있다.

이번 실험의 목적은 **게시글이 누적되는 상황에서 현재 구현한 LIKE 검색이 적절한 응답시간을 유지할 수 있는지 검증하는 것**이다. 먼저 데이터 규모에 따른 변화를 확인하고, 이후 동시 검색 요청을 늘려 일반 게시글 조회에 미치는 영향도 관측한다.

결과가 드물거나 없는 검색에서는 결과를 찾거나 없음을 판단하기까지 많은 게시글을 확인해 지연이 커질 수 있다고 가정한다. 검색어가 최신 글에 몰린 경우와 과거 글에 흩어진 경우도 비교해 실제 읽은 행 수와 응답시간의 관계를 확인한다.

데이터 누적과 검색 집중은 실험을 위한 가정이다. 대량 데이터의 검색 성능은 아직 측정하지 않았다. 시험 결과에서 지연 조건을 찾고, 원인 분석과 개선·재시험의 근거로 남긴다.

## 2. 어떤 검색을 기준으로 비교할 것인가?

| 항목 | 확정한 동작 |
|---|---|
| 검색 범위·일치 규칙 | 검색어를 공백으로 나누고, 각 단어가 같은 게시글의 제목 또는 본문에 부분 일치해야 한다. 모든 단어 조건을 만족한 글을 반환한다. |
| 정렬 | 기존 게시글 ID 내림차순을 유지한다. |
| 페이지 이동 | 기존 커서를 사용한다. 검색어를 바꾸면 첫 페이지부터 조회하고, 다음 페이지는 같은 검색어를 보낸다. |
| 결과 검증 | 제목·본문에 단어가 나뉜 글, 일부 단어만 있는 글, 결과가 없는 검색어를 구분한다. |

현재 API는 검색어가 있는 `GET /posts` 요청으로 시험한다. 성능 비교 시 호출 조건과 페이지 크기를 고정하고, 첫 페이지와 커서로 요청하는 다음 페이지를 구분한다.

## 3. 목표와 시험 순서를 어떻게 정할 것인가?

검색 API와 화면 연결을 완료했으므로, 먼저 사용자 경험 목표와 시험 조건을 정한다. 이어서 데이터 규모와 요청 조건을 바꿔 어떤 상황에서 목표를 유지하는지 확인한다.

### 사용자에게 어느 정도의 응답시간을 제공할 것인가?

Nielsen Norman Group은 약 1초를 지연을 인지하더라도 사용자의 사고 흐름이 유지되는 대략적인 경계로 설명한다. 경기 중 선수와 장면에 대한 게시글을 연이어 찾는 흐름에 이를 적용해 초기 응답시간 목표를 정했다. 이 목표는 사용성 자료를 참고한 설계 판단이다. [응답시간 가이드](https://www.nngroup.com/articles/response-times-3-important-limits/)

> **결정**
>
> 각 시험 구간의 유효한 검색 중 99% 이상이, 돋보기나 Enter로 검색을 확정한 순간부터 정상 결과 목록 또는 결과 없음이 화면에 표시되기까지 1초 이내에 완료되는 것을 초기 SLO로 설정한다.
>
> 첫 결과와 스크롤로 요청하는 다음 결과의 시간을 구분해서 확인한다.

| 구분 | 측정·판단 방법 | 현재 상태 |
|---|---|---|
| 화면 응답시간 | 검색 확정부터 결과 표시까지 측정한다. 네트워크·API·화면 처리 시간을 포함한다. | 1초 이내 목표 확정 |
| 지연 SLI | 유효한 검색 요청 중 1초 이내에 정상 결과를 표시한 비율을 측정한다. | 측정 대상 정의 |
| SLO 달성 비율과 평가 구간 | 각 시험 구간에서 1초 이내 정상 완료 비율 99% 이상을 목표로 한다. | 99% 확정, 평가 구간 미확정 |
| API 응답시간 | HTTP 요청·응답 시간을 측정하고 P50·P95·P99를 기록한다. 화면 목표 안에서 API 시간 예산을 정한다. | 수치 목표 미확정 |
| 오류와 정확성 | 정상 검색 응답 비율과 5xx·네트워크 실패·타임아웃을 기록하고, 예상 결과와 페이지 누락·중복을 확인한다. | 별도 허용 실패율 미확정, k6 측정 상한 120초 우선 적용 |

99%는 느리거나 실패한 검색을 합쳐 최대 1%까지 허용하는 초기 설계 판단으로 선택했다. 1초의 사용성 근거와 달성 비율의 선택 근거를 구분한다. 유효한 검색 10,000건을 평가한다면 최소 9,900건이 1초 이내에 정상 결과를 표시해야 한다.

먼저 k6 HTTP로 검색 API의 기준 성능을 측정한다. 화면 표시 시간은 검색 버튼 또는 Enter 입력부터 새 결과 목록이나 ‘결과 없음’이 처음 보일 때까지 별도로 잰다. 대표 조건은 개선 전후 같은 부하에서 비교한다. 단건은 Chrome DevTools의 Performance 탭에서 Screenshots를 켜고 녹화해 입력 시점과 새 결과가 처음 보이는 프레임을 확인한다. Network 탭에서는 검색 API의 응답시간을 따로 확인한다. 화면 SLO 달성률은 브라우저에서 검색 흐름을 반복해 집계한다. [Chrome DevTools Performance](https://developer.chrome.com/docs/devtools/performance/reference/)

검색 결과가 1초를 넘어도 응답을 계속 기다린다. 기준 측정에서는 30초가 넘는 응답도 관찰할 수 있도록 k6 HTTP 요청에 측정용 타임아웃 120초를 우선 적용한다. 이 상한은 시험 설정이며 1초 화면 목표와 구분한다. 상한 전에 정상 응답을 받으면 실제 소요 시간을 기록하고, 상한까지 응답이 없으면 타임아웃으로 별도 집계한다. 서버나 Nginx가 먼저 연결을 끊거나 오류를 반환하면 해당 시점과 실패 유형을 기록한다. 개선 전후에는 같은 타임아웃을 사용해 P99와 타임아웃 건수를 비교한다. 빠르게 실패한 응답도 실패로 집계하고, 결과가 없는 검색의 정상 빈 목록은 정상 결과로 처리한다. [k6 HTTP 요청 옵션](https://grafana.com/docs/k6/latest/javascript-api/k6-http/params/)

### 어떤 순서로 측정할 것인가?

| 단계 | 확인할 내용 | 남길 근거 |
|---|---|---|
| 1. 시험 기준 확정 | 데이터 규칙, 달성 비율, 실패율, 시험 구간과 요청 조건을 정한다. | 목표의 이유와 실행 조건 |
| 2. 소규모 데이터 검증 | 적재 시간·용량과 예상 검색 결과를 확인한다. | 데이터 생성 규칙과 정답 목록 |
| 3. 단일 요청 기준 측정 | 데이터 규모별로 같은 검색어를 반복한다. | API·SQL 시간, 실행 계획, 실제 읽은 행 수 |
| 4. 지연 원인 분석 | 느린 검색의 실행 과정과 API·SQL 시간 차이를 추적한다. | 지연이 커지는 조건과 원인 근거 |
| 5. 동시 요청 측정 | 검색 요청량을 단계적으로 늘리고 일반 목록 조회도 확인한다. | 지연·처리량·실패율과 자원 사용량 |
| 6. 개선·재시험 | 원인에 맞는 변경을 하나씩 적용하고 같은 조건에서 비교한다. | 개선 효과, 검색 결과 차이와 남는 비용 |

데이터 규모는 1만 → 10만 → 100만 건으로 단계적으로 늘려 비교한다. 먼저 1만 건에서 생성 규칙·검색 결과·적재 시간과 용량을 확인한다. 게시글 누적만으로 LIKE 검색 비용이 커지는 조건을 확인하기 위해, 검색어·정렬·페이지 크기를 고정하고 각 규모에서 동시 부하 없이 기준 성능을 측정한다. 개선하기 전에 세 규모의 결과를 모두 남겨, 같은 데이터 규모에서 개선 전후를 비교할 수 있게 한다. 100만 건에서는 같은 데이터에 배치해 둔 위치 비교용 검색어도 측정한다. 이후 낮은 동시 부하부터 시작해 지속 목표와 순간 피크를 순서대로 확인한다. 동시 부하 시험은 아래 확정한 시간과 반복 조건을 적용한다.

### 경기 중 예상 검색 부하는 어떻게 산정했는가?

HikariCP 실험에서 사용한 MAU·DAU·세션 가정을 재사용하고, 이번 검색 기능의 이용 비율과 요청 횟수를 추가한다. 기존 자료는 피크 1시간에 시작되는 세션을 정의했다. 10분으로 환산할 때도 세션 수로 계산한다. [기존 트래픽 산정 기록](https://app.notion.com/p/8-3-3b181eafed0b80c49912c3140041e7ef?source=copy_link)

| 항목 | 적용한 값 | 근거 구분 |
|---|---|---|
| MAU | 100만 명 | 기존 서비스 규모 가정 |
| DAU / MAU | 20% | 기존 활성 비율 가정 |
| 사용자당 하루 세션 | 1.5회 | 기존 행동 가정 |
| 피크 1시간 세션 비중 | 하루 전체의 20% | 기존 집중도 가정 |
| 순간 집중 계수 | 지속 피크의 2배 | 기존 순간 피크 가정 |
| 검색을 이용하는 세션 비율 | 10% | 이번 시험에서 선택한 가정 |
| 검색 세션당 검색 확정 | 3회 | 검색어를 바꿔 재검색하는 행동을 포함한 가정 |

```text
하루 세션 = 1,000,000 × 20% × 1.5 = 300,000회
피크 1시간 세션 = 300,000 × 20% = 60,000회
피크 1시간 검색 요청 = 60,000 × 10% × 3 = 18,000건

지속 검색 부하 = 18,000 ÷ 3,600 = 5 RPS
순간 검색 부하 = 5 × 2 = 10 RPS
```

검색 이용 비율 10%와 3회는 실측값이 아닌 초기 시험 가정이다. 세션의 일부가 검색을 사용하고, 검색하는 세션은 선수명과 장면을 바꾸어 재검색한다고 가정했다. 위 5·10 RPS는 검색 확정으로 발생하는 첫 페이지 요청을 기준으로 한다. 스크롤 추가 로딩을 포함한 검색 API 요청량은 아래 탐색 깊이 가정으로 계산한다.

> **결정**
>
> 검색 확정 유입은 지속 5회/s·순간 10회/s로 설정한다. 결과가 충분하고 탐색 흐름이 유지되는 조건에서 페이지 조회를 포함한 검색 API 요청량은 평균 지속 25.5 RPS·순간 51 RPS로 예상한다. 1만·10만·100만 건에서 같은 이용 가정을 적용해 비교한다.

동시 부하 시험은 검색 시작 5회/s로 워밍업 2분·지속 측정 5분을 진행하고, 10회/s 피크 1분 뒤 5회/s 회복 2분을 관측한다. 총 10분 구성을 같은 조건으로 3회 반복한다. 피크 진입과 회복 시 검색 시작 속도를 즉시 바꾸며, 이미 시작한 사용자의 후속 페이지 요청은 이어진다. 예상 부하를 충족한 뒤 처리 한계를 탐색할 추가 요청량은 결과를 보고 결정한다.

#89의 동시 부하 시험은 김민재·오버래핑·아약스를 각각 약 ⅓로 선택한다. 사용자 검색 빈도의 실측값이 없으므로, 조건별 표본을 비슷하게 확보하기 위한 시험 분포로 정했다. 요청 시작 시각을 기준으로 워밍업·지속·피크·회복을 구분하고, 검색 흐름을 시작한 구간도 함께 기록한다. 결과가 없는 검색은 한 번에 끝나고 드문 검색도 결과가 소진되면 종료하므로 실제 API 요청률을 측정해 남긴다.

### 검색 결과를 얼마나 내려보는가?

한 페이지는 현재 화면과 동일하게 5건으로 고정한다. 각 검색 확정 후 결과를 탐색하는 깊이는 다음 비율로 선택한다.

| 최대 확인 게시글 | 추가 페이지 로딩 | 첫 페이지 포함 API 요청 | 비율 |
|---|---|---|---|
| 10건 | 1회 | 2건 | 30% |
| 25건 | 4회 | 5건 | 50% |
| 50건 | 9회 | 10건 | 20% |

```text
검색 확정 1회당 평균 페이지 요청 = 2 × 30% + 5 × 50% + 10 × 20% = 5.1건
지속 검색 API 요청량 = 5 × 5.1 = 25.5 RPS
순간 검색 API 요청량 = 10 × 5.1 = 51 RPS
```

탐색 깊이는 결과를 여러 페이지 살펴보는 이용을 표현한 시험 가정이다. 결과가 충분할 때의 평균 요청량이며, 결과 없음 또는 `has_next=false`이면 탐색을 종료한다. 검색어 조건별 실제 페이지 요청 수와 도달 RPS도 기록한다.

사용자 흐름 시험에서는 현재 페이지의 검색 결과 5건을 받은 뒤 제목을 훑어보는 시간으로 2~5초를 기다린다. 다음 페이지가 있고 목표 탐색 깊이에 도달하기 전이면 응답의 커서로 다음 5건을 요청한다. 순간 구간의 실제 RPS는 앞선 검색 흐름의 후속 요청과 읽는 시간의 영향을 받으므로, 51 RPS는 위 가정의 계산값으로 남기고 실제 구간별 요청률을 함께 확인한다.

### 테스트 데이터

- 고정된 seed로 같은 데이터를 다시 생성할 수 있는 스크립트를 작성한다.
- 최종적으로 2년 동안 게시글 100만 건이 누적된 시험 상황을 가정한다. 작은 규모에서 적재 시간·용량을 먼저 확인한다.
- 제목·본문 길이와 검색어 등장 빈도를 조절한다. 같은 문장을 반복 복사한 데이터만으로 결과를 내지 않는다.
- 결과가 많은 검색어, 적은 검색어, 결과가 없는 검색어와 여러 단어 검색어를 포함한다.
- 규모 비교용 검색어는 고르게 배치한다. 위치 비교용 검색어는 같은 데이터에 미리 배치하고, 100만 건에서만 측정한다.
- 같은 데이터 세트와 검색어 목록을 검색 방식별 비교에 재사용한다.

제목은 5~30자로 생성한다. 제목 상한은 게시글 작성 API의 검증 규칙과 검색 DB의 `posts.title` 컬럼에 맞춘다. 제목과 본문 길이는 공백과 줄바꿈을 포함한 문자 수로 계산한다. 게시글별 생성 길이는 다음 구간을 따르며, 전체 데이터에 각 비율을 적용한다.

| 구분 | 본문 길이 | 비율 | 표현할 글 유형 |
|---|---|---|---|
| 짧은 글 | 1~200자 | 70% | 경기 중 반응, 짧은 질문·감상, 미디어의 짧은 설명 |
| 일반 글 | 201~999자 | 25% | 선수 소식, 설명이 붙은 감상·의견 |
| 긴 글 | 1,000~3,000자 | 5% | 여러 문단의 전술 분석·경기 후기 |

공개 스포츠 커뮤니티에서 짧은 반응·소식·분석·후기 글이 섞이는 모습을 참고해 정한 실험용 분포다. 70%·25%·5%와 길이 경계는 우리 시험에서 선택한 가정이다. [게시판 유형 참고](https://theqoo.net/sonheungmin) · [매치리포트 참고](https://serieamania.com/g2/bbs/board.php?bo_table=matchreport)

검색어별로 제목 또는 본문에 해당 문자열이 포함된 게시글 비율을 조절한다. 같은 글의 제목과 본문에 모두 등장해도 일치 게시글 한 건으로 센다.

| 검색 조건 | 일치 비율 | 1만 건 | 10만 건 | 100만 건 |
|---|---|---|---|---|
| 자주 등장하는 검색어 | 10% | 1,000건 | 10,000건 | 100,000건 |
| 드문 검색어 | 0.1% | 10건 | 100건 | 1,000건 |
| 결과가 없는 검색어 | 0% | 0건 | 0건 | 0건 |

10%·0.1%는 결과 빈도에 따른 비용 차이를 비교하기 위해 선택한 시험값이다. 검색어별 일치 비율을 유지해 데이터 규모 증가의 영향을 비교한다. 여러 검색어가 같은 글에 함께 등장할 수 있으며, 특정 검색어와 일치하지 않는 글도 다른 선수·경기 내용으로 채운다. 결과가 없는 검색어는 전체 제목·본문 어디에도 포함되지 않도록 검증한다.

게시글마다 작성 시각(`created_at`)을 지정하고 오래된 글부터 삽입해, ID가 클수록 작성 시각도 최신이 되도록 맞춘다. 최종 100만 건의 작성 시각은 2년 범위에 배치한다. 2년·100만 건은 검색 시험을 위한 누적 데이터 가정으로 정했다.

오래된 글부터 첫 1만 건을 적재하고, 다음 9만 건을 추가해 10만 건, 이후 90만 건을 추가해 100만 건으로 진행한다. 규모 비교에서는 각 단계의 게시글 전체에 일치 글을 고르게 배치하고, 검색어별 일치 비율을 유지한다.

### 100만 건에서 검색어 위치를 어떻게 비교하는가?

100만 건을 한 번 누적 적재하면서 위치 비교용 검색어 두 개를 미리 배치한다. 규모 비교에는 기존 검색어 목록을 사용하고, 위치 비교용 두 검색어는 100만 건 적재와 검증이 끝난 뒤에만 사용한다.

| 용도 | 검색어 | 최종 데이터에서의 배치 | 구간 내 일치 | 구간 밖 일치 |
|---|---|---|---:|---:|
| 과거 집중 | 정우영 | 작성 순서 1~200,000번째 | 100,000건 | 0건 |
| 최신 집중 | 황희찬 | 작성 순서 800,001~1,000,000번째 | 100,000건 | 0건 |

작성 순서 기준으로 각 대상 구간의 1,000건마다 일치할 글 500건을 고정된 시드로 섞는다. 첫 1만 건에는 정우영 일치 글 5,000건이 들어가고, 황희찬은 마지막 20만 건부터 등장한다. 일반 문장 생성에서는 두 이름을 제외하고, 지정된 글에만 삽입한다. 두 이름은 글자 수가 같으며, 제목·본문에 배치하는 비율과 일치 게시글의 길이 분포도 동일하게 맞춘다.

적재 후 실제 LIKE 조건으로 제목과 본문을 조회해 두 검색어의 전체 일치 건수와 지정 구간 밖 0건을 검증한다. 같은 DB에서 각각 최신순 첫 5건을 요청해 API 응답시간과 실행 계획의 읽은 행 수를 비교한다. 검색어가 서로 다르므로 현재 LIKE 검색에서 배치에 따른 차이를 보는 시험으로 해석한다.

### 시험 검색어를 어떻게 구성할 것인가?

선수명·경기 장면·전술 용어를 섞어 단일 검색어 21개를 사용한다. 일치 비율은 각 검색어에 개별적으로 적용한다. 같은 글이 여러 검색어와 일치하는 것은 허용한다.

| 일치 빈도 | 단일 검색어 |
|---|---|
| 10% | 손흥민, 토트넘, 프리킥, 이강인, 파리생제르맹, 페널티킥, 김민재, 바이에른뮌헨, 코너킥 |
| 0.1% | 오버래핑, 언더래핑, 라볼피아나, 역압박, 게겐프레싱, 카테나치오, 하프스페이스, 인버티드풀백, 제로톱 |
| 0% | 즐라탄, 아약스, 라보나 |

0% 검색어는 생성되는 모든 제목과 본문에서 제외하고 검증한다. 단어별 일치 건수와 분포는 각 적재 단계에서 확인한다.

여러 단어 검색은 기준 검색어가 포함된 게시글 중 두 번째 단어도 포함하는 비율을 정한다. 세 기준 검색어의 전체 일치 비율은 각각 10%로 둔다.

| 검색어 | 기준 검색어 포함 글 중 두 단어 일치 비율 | 전체 일치 비율 | 1만 건 | 10만 건 | 100만 건 |
|---|---:|---:|---:|---:|---:|
| 손흥민 골 | 20% | 2% | 200건 | 2,000건 | 20,000건 |
| 김민재 수비 | 20% | 2% | 200건 | 2,000건 | 20,000건 |
| 이강인 도움 | 2% | 0.2% | 20건 | 200건 | 2,000건 |

앞의 두 조합은 같은 일치 빈도에서 검색어를 바꿔 비교하고, 마지막 조합으로 일치 빈도가 낮은 조건을 확인한다. 이 비율은 벤치마크용 가정이다.

규모 비교에서는 다중 검색어 세 조합도 작성 순서 전체에 고르게 분포하도록 구성한다. 각 적재 규모에서 제목·본문을 통틀어 두 단어를 모두 만족하는 게시글의 수와 작성 시점 분포를 확인한다.

시험 스크립트가 같은 조건을 다시 사용할 수 있도록 검색어·일치 비율·배치·예상 건수를 목록으로 관리하고, 적재 후 실제 결과와 대조한다.

### 측정 항목

| 확인할 질문 | 측정·검증 항목 |
|---|---|
| 원하는 글을 찾는가? | 예상 게시글 포함 여부, 의도하지 않은 결과, 페이지 간 누락·중복 |
| 데이터가 늘면 얼마나 느려지는가? | 검색 API P50·P95·P99, SQL 실행시간, 실행 계획과 실제 읽은 행 수 |
| 검색이 몰리면 어떻게 되는가? | 요청량별 응답시간·처리량·실패율, DB CPU·메모리·디스크 I/O |
| 일반 조회도 영향을 받는가? | 검색과 함께 실행한 일반 게시글 조회의 응답시간·실패율 |
| 측정값이 반복되는가? | 워밍업 조건, 반복 실행 결과와 편차, 부하 생성기 자원 사용량 |

단일 요청 시험에서 느린 조건을 찾으면, MySQL에서 같은 검색어·커서·정렬·제한을 적용한 실제 검색 SQL에 `EXPLAIN ANALYZE`를 붙여 실행한다. 실행 계획을 얻기 위해 미리 켜둘 설정은 없다. 스캔과 필터 단계별 실제 시간·행 수·반복 횟수를 확인한다. 스캔 단계가 넘긴 행 수와 최종 반환 행 수를 구분한다. [MySQL 실행 계획](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

동시 부하 중 실제로 실행된 느린 SQL을 수집하는 시험에서는 슬로우 쿼리 로그를 미리 켜고 기록 기준 시간(`long_query_time`)을 정한다. 로그의 `Query_time`과 `Rows_examined`로 해당 SQL의 실행시간과 MySQL 서버가 확인한 행 수를 남긴다. 개선 전후에는 로깅 조건을 동일하게 맞춘다. [MySQL 슬로우 쿼리 로그](https://dev.mysql.com/doc/refman/8.4/en/slow-query-log.html)

서버 사양·애플리케이션 버전·DB 설정·데이터·검색어·요청량을 기록한다. 목표 응답시간과 오류율 기준은 본격적인 비교 실험 전에 정하고, 시험 조건별 결과를 남긴다.

## 4. 측정 결과에 따라 어떻게 개선할 것인가?

기본 검색에서 비용이 큰 구간을 확인한 뒤 필요한 개선을 적용한다. 여러 변경을 한꺼번에 적용하지 않고 각 변경의 효과와 대가를 비교한다.

| 개선 후보 | 적용을 검토할 조건 | 함께 확인할 내용 |
|---|---|---|
| 쿼리·일반 인덱스 | 조건·정렬·조인에서 불필요하게 많은 데이터를 읽는 경우 | 실행 계획, 읽은 행 수, 인덱스 용량과 쓰기 비용 |
| 애플리케이션 처리 | 불필요한 필드·중복 쿼리·결과 가공이 비용을 만드는 경우 | API와 SQL 실행시간의 차이, 쿼리 수, 메모리 |
| MySQL FULLTEXT | LIKE의 문자열 조건 확인 비용이 주요 병목인 경우 | ngram 등 한국어 색인 방식, 검색 결과 차이, 색인 크기·작성 비용 |
| 캐싱 | 같은 검색 조건의 요청이 반복되는 경우 | 적중률, DB 요청 감소, 만료 시 부하, 게시글 변경 반영 |
| Elasticsearch | MySQL 개선 후에도 성능·검색 품질 요구가 남는 경우 | 검색 품질·지연, 추가 자원, 초기 색인과 변경 동기화 비용 |

일반 인덱스 추가만으로 `LIKE '%검색어%'`가 빨라질 것이라고 가정하지 않는다. 실제로 활용되는 인덱스와 줄어든 작업량을 확인한다.

검색 방식 간 성능은 우선 캐시 없이 비교한다. 캐싱 효과는 반복 검색 조건을 별도로 만들어 확인한다. FULLTEXT·Elasticsearch로 검색 결과의 의미가 바뀌면 속도와 결과 품질을 각각 평가한다.

## 5. Elasticsearch와 검색 품질은 어디까지 확장할 것인가?

LIKE와 MySQL 내부 개선의 결과를 바탕으로 다음 범위를 정한다. 아래 항목은 확장 후보이며, 모든 기능의 구현을 완료 기준으로 삼지는 않는다.

- 한국어 분석과 검색어 표현 차이 대응
- 오타 보정과 연관 검색어 제안
- 최신순 외의 검색 결과 랭킹
- 사용자 의도와 유사한 표현의 게시글 검색

현재 데이터와 검색어 21개는 LIKE 기준 성능을 남기고 FULLTEXT·Elasticsearch와 비교할 때 재사용한다. 검색 방식이 달라지면 단어 분석과 부분 일치 규칙에 따른 결과 차이를 확인하고, 속도와 결과 품질을 함께 기록한다.

연관 검색어·오타 보정·의도 검색은 해당 단계에서 평가용 검색어와 기대 결과를 추가한다. 예를 들어 오타가 있는 검색어, 선수의 별명, 표현은 달라도 같은 경기 장면을 찾는 질의를 별도로 구성한다. 연관 검색어의 기대 조합과 추천 순위도 기록한다. 현재 만든 등장 비율은 시험 데이터의 분포이며, 사용자 검색 빈도는 향후 검색 로그나 명시적인 이용 가정으로 별도 정의한다.

Elasticsearch를 도입하면 기존 게시글의 초기 색인과 새 글·수정·삭제의 반영 경로도 필요하다. 변경 반영 지연, 누락·중복, 재시도와 재색인을 검증 범위에 포함한다.

## 6. 결과를 어떻게 남길 것인가?

각 시험에는 코드 커밋, 서버 사양·DB 설정, 데이터 생성 버전과 seed, 검색어·페이지 조건, 요청량·워밍업·시험 시간과 반복 횟수를 남긴다. 원본 측정 결과와 실행 계획을 함께 보관해 개선 전후를 같은 조건으로 비교한다.

확인한 현상 → 원인 근거 → 개선 선택 이유 → 재시험 결과 → 남은 한계 순서로 정리한다. 프로젝트 간 재사용할 판단과 실수 방지 항목은 작업 완료 후 독스 레포에 추려 기록한다.

- [x] 기준 측정의 k6 HTTP 타임아웃은 120초로 우선 설정

- [ ] 단계별 일치 건수와 100만 건 위치 조건을 만족하는 생성 규칙 구현·검증
- [x] 검색 결과 목록을 훑어본 뒤 다음 페이지 요청까지 2~5초 대기

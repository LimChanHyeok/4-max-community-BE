# 게시글 LIKE 검색 성능 검증 계획

**기준 브랜치** `search-enhancement` · **상태** 시험 조건 구체화 중

현재 구현한 제목·본문 LIKE 검색을 기준으로 데이터 증가에 따른 한계를 확인하고, 측정 결과를 근거로 개선한다. 계획과 시험 코드·측정 결과를 이 저장소에서 함께 관리한다.

**진행 흐름**

목적·목표 정의 → 데이터·시험 조건 확정 → 소규모 적재 검증 → 기준 성능 측정 → 원인 분석 → 개선·재시험

## 1. 무엇을 확인하려는가?

제목·본문 LIKE 검색 API와 검색 화면 연결, 브라우저 뒤로 가기 복원을 완료했다. 백엔드 EC2와 MySQL EC2를 각각 한 대씩 사용하는 실험 환경에서 검색 성능을 검증한다.

### 어떤 상황을 검증하려는가?

경기 직후에는 특정 선수나 경기 장면을 찾는 검색이 집중될 수 있다. 게시글이 누적되면 같은 검색어를 사용하더라도 조건 확인과 정렬에 필요한 작업이 늘어날 수 있다.

이번 실험의 목적은 **게시글이 누적되는 상황에서 현재 구현한 LIKE 검색이 적절한 응답시간을 유지할 수 있는지 검증하는 것**이다. 먼저 데이터 규모에 따른 변화를 확인하고, 이후 동시 검색 요청을 늘려 일반 게시글 조회에 미치는 영향도 관측한다.

결과가 드물거나 없는 검색에서는 결과를 찾거나 없음을 판단하기까지 많은 게시글을 확인해 지연이 커질 수 있다고 가정한다. 검색어가 최신 글에 몰린 경우와 과거 글에 흩어진 경우도 비교해 실제 읽은 행 수와 응답시간의 관계를 확인한다.

데이터 누적과 검색 집중은 실험을 위한 가정이다. 대량 데이터의 검색 성능은 아직 측정하지 않았다. 시험 결과에서 지연 조건을 찾고, 원인 분석과 개선·재시험의 근거로 남긴다.

## 2. 어떤 검색을 기준으로 비교할 것인가?

| 항목 | 확정한 동작 |
|---|---|
| 검색 범위·일치 규칙 | 검색어를 공백으로 나누고, 각 단어가 같은 게시글의 제목 또는 본문에 부분 일치해야 한다. 모든 단어 조건을 만족한 글을 반환한다. |
| 정렬 | 기존 게시글 ID 내림차순을 유지한다. |
| 페이지 이동 | 기존 커서를 사용한다. 검색어를 바꾸면 첫 페이지부터 조회하고, 다음 페이지는 같은 검색어를 보낸다. |
| 결과 검증 | 제목·본문에 단어가 나뉜 글, 일부 단어만 있는 글, 결과가 없는 검색어를 구분한다. |

현재 API는 검색어가 있는 `GET /posts` 요청으로 시험한다. 성능 비교 시 호출 조건과 페이지 크기를 고정하고, 첫 페이지와 커서로 요청하는 다음 페이지를 구분한다.

## 3. 목표와 시험 순서를 어떻게 정할 것인가?

검색 API와 화면 연결을 완료했으므로, 먼저 사용자 경험 목표와 시험 조건을 정한다. 이어서 데이터 규모와 요청 조건을 바꿔 어떤 상황에서 목표를 유지하는지 확인한다.

### 사용자에게 어느 정도의 응답시간을 제공할 것인가?

Nielsen Norman Group은 약 1초를 지연을 인지하더라도 사용자의 사고 흐름이 유지되는 대략적인 경계로 설명한다. 경기 중 선수와 장면에 대한 게시글을 연이어 찾는 흐름에 이를 적용해 초기 응답시간 목표를 정했다. 이 목표는 사용성 자료를 참고한 설계 판단이다. [응답시간 가이드](https://www.nngroup.com/articles/response-times-3-important-limits/)

> **결정**
>
> 검색을 돋보기나 Enter로 확정한 순간부터 결과 목록 또는 결과 없음이 화면에 표시되기까지 1초 이내를 초기 사용자 경험 목표로 설정한다.
>
> 첫 결과와 스크롤로 요청하는 다음 결과의 시간을 구분해서 확인한다.

| 구분 | 측정·판단 방법 | 현재 상태 |
|---|---|---|
| 화면 응답시간 | 검색 확정부터 결과 표시까지 측정한다. 네트워크·API·화면 처리 시간을 포함한다. | 1초 이내 목표 확정 |
| 지연 SLI | 유효한 검색 요청 중 1초 이내에 정상 결과를 표시한 비율을 측정한다. | 측정 대상 정의 |
| SLO 달성 비율과 평가 구간 | 어느 비율을 만족해야 하는지와 평가할 시험 구간을 정한다. | 시험 전에 확정 |
| API 응답시간 | HTTP 요청·응답 시간을 측정하고 P50·P95·P99를 기록한다. 화면 목표 안에서 API 시간 예산을 정한다. | 수치 목표 미확정 |
| 오류와 정확성 | 정상 검색 응답 비율과 5xx·네트워크 실패·타임아웃을 기록하고, 예상 결과와 페이지 누락·중복을 확인한다. | 허용 실패율과 타임아웃 미확정 |

API 응답시간은 화면 표시까지 걸린 시간의 일부다. HTTP 부하 시험과 브라우저의 실제 화면 표시 측정을 함께 기록한다. 빠르게 실패한 응답도 실패로 집계하고, 결과가 없는 검색의 정상 빈 목록은 정상 결과로 처리한다.

### 어떤 순서로 측정할 것인가?

| 단계 | 확인할 내용 | 남길 근거 |
|---|---|---|
| 1. 시험 기준 확정 | 데이터 규칙, 달성 비율, 실패율, 시험 구간과 요청 조건을 정한다. | 목표의 이유와 실행 조건 |
| 2. 소규모 데이터 검증 | 적재 시간·용량과 예상 검색 결과를 확인한다. | 데이터 생성 규칙과 정답 목록 |
| 3. 단일 요청 기준 측정 | 데이터 규모별로 같은 검색어를 반복한다. | API·SQL 시간, 실행 계획, 실제 읽은 행 수 |
| 4. 지연 원인 분석 | 느린 검색의 실행 과정과 API·SQL 시간 차이를 추적한다. | 지연이 커지는 조건과 원인 근거 |
| 5. 동시 요청 측정 | 검색 요청량을 단계적으로 늘리고 일반 목록 조회도 확인한다. | 지연·처리량·실패율과 자원 사용량 |
| 6. 개선·재시험 | 원인에 맞는 변경을 하나씩 적용하고 같은 조건에서 비교한다. | 개선 효과, 검색 결과 차이와 남는 비용 |

규모별 단계는 1만 → 10만 → 100만 건을 초안으로 두고, 작은 적재의 시간과 용량을 확인한 뒤 확정한다. 동시 요청량·워밍업·반복 횟수·시험 시간도 시험 전에 정한다.

### 테스트 데이터

- 고정된 seed로 같은 데이터를 다시 생성할 수 있는 스크립트를 작성한다.
- 최종 100만 건 이상을 적재하되, 작은 규모에서 적재 시간·용량을 먼저 확인한다.
- 제목·본문 길이와 검색어 등장 빈도를 조절한다. 같은 문장을 반복 복사한 데이터만으로 결과를 내지 않는다.
- 결과가 많은 검색어, 적은 검색어, 결과가 없는 검색어와 여러 단어 검색어를 포함한다.
- 결과가 있는 검색어는 최신·과거 글의 분포도 조절한다. 결과 빈도·분포·제목과 본문의 길이 비율은 적재 전에 정한다.
- 같은 데이터 세트와 검색어 목록을 검색 방식별 비교에 재사용한다.

### 측정 항목

| 확인할 질문 | 측정·검증 항목 |
|---|---|
| 원하는 글을 찾는가? | 예상 게시글 포함 여부, 의도하지 않은 결과, 페이지 간 누락·중복 |
| 데이터가 늘면 얼마나 느려지는가? | 검색 API P50·P95·P99, SQL 실행시간, 실행 계획과 실제 읽은 행 수 |
| 검색이 몰리면 어떻게 되는가? | 요청량별 응답시간·처리량·실패율, DB CPU·메모리·디스크 I/O |
| 일반 조회도 영향을 받는가? | 검색과 함께 실행한 일반 게시글 조회의 응답시간·실패율 |
| 측정값이 반복되는가? | 워밍업 조건, 반복 실행 결과와 편차, 부하 생성기 자원 사용량 |

서버 사양·애플리케이션 버전·DB 설정·데이터·검색어·요청량을 기록한다. 목표 응답시간과 오류율 기준은 본격적인 비교 실험 전에 정하고, 시험 조건별 결과를 남긴다.

## 4. 측정 결과에 따라 어떻게 개선할 것인가?

기본 검색에서 비용이 큰 구간을 확인한 뒤 필요한 개선을 적용한다. 여러 변경을 한꺼번에 적용하지 않고 각 변경의 효과와 대가를 비교한다.

| 개선 후보 | 적용을 검토할 조건 | 함께 확인할 내용 |
|---|---|---|
| 쿼리·일반 인덱스 | 조건·정렬·조인에서 불필요하게 많은 데이터를 읽는 경우 | 실행 계획, 읽은 행 수, 인덱스 용량과 쓰기 비용 |
| 애플리케이션 처리 | 불필요한 필드·중복 쿼리·결과 가공이 비용을 만드는 경우 | API와 SQL 실행시간의 차이, 쿼리 수, 메모리 |
| MySQL FULLTEXT | LIKE의 문자열 조건 확인 비용이 주요 병목인 경우 | ngram 등 한국어 색인 방식, 검색 결과 차이, 색인 크기·작성 비용 |
| 캐싱 | 같은 검색 조건의 요청이 반복되는 경우 | 적중률, DB 요청 감소, 만료 시 부하, 게시글 변경 반영 |
| Elasticsearch | MySQL 개선 후에도 성능·검색 품질 요구가 남는 경우 | 검색 품질·지연, 추가 자원, 초기 색인과 변경 동기화 비용 |

일반 인덱스 추가만으로 `LIKE '%검색어%'`가 빨라질 것이라고 가정하지 않는다. 실제로 활용되는 인덱스와 줄어든 작업량을 확인한다.

검색 방식 간 성능은 우선 캐시 없이 비교한다. 캐싱 효과는 반복 검색 조건을 별도로 만들어 확인한다. FULLTEXT·Elasticsearch로 검색 결과의 의미가 바뀌면 속도와 결과 품질을 각각 평가한다.

## 5. Elasticsearch와 검색 품질은 어디까지 확장할 것인가?

LIKE와 MySQL 내부 개선의 결과를 바탕으로 다음 범위를 정한다. 아래 항목은 확장 후보이며, 모든 기능의 구현을 완료 기준으로 삼지는 않는다.

- 한국어 분석과 검색어 표현 차이 대응
- 오타 보정과 연관 검색어 제안
- 최신순 외의 검색 결과 랭킹
- 사용자 의도와 유사한 표현의 게시글 검색

Elasticsearch를 도입하면 기존 게시글의 초기 색인과 새 글·수정·삭제의 반영 경로도 필요하다. 변경 반영 지연, 누락·중복, 재시도와 재색인을 검증 범위에 포함한다.

## 6. 결과를 어떻게 남길 것인가?

각 시험에는 코드 커밋, 서버 사양·DB 설정, 데이터 생성 버전과 seed, 검색어·페이지 조건, 요청량·워밍업·시험 시간과 반복 횟수를 남긴다. 원본 측정 결과와 실행 계획을 함께 보관해 개선 전후를 같은 조건으로 비교한다.

확인한 현상 → 원인 근거 → 개선 선택 이유 → 재시험 결과 → 남은 한계 순서로 정리한다. 프로젝트 간 재사용할 판단과 실수 방지 항목은 작업 완료 후 독스 레포에 추려 기록한다.
